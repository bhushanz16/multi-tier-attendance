Module 1: Problem Identification, Requirement Engineering & System Design Phase

1. Problem Identification & Feasibility Study

1.1 Identification of a Real-World Problem

Traditional attendance tracking mechanisms (roll calls, paper sheets) in dense academic environments suffer from profound logistical inefficiencies. In a standard 50-minute lecture with 100 students, manual roll calls consume up to 20% of instructional time. Furthermore, paper-based ledgers are highly vulnerable to proxy attendance, leading to skewed academic analytics and institutional data integrity loss.

1.2 Problem Justification

The implementation of an automated, biometric facial-recognition platform justifies itself by entirely eliminating human error and proxy attendance. By leveraging the existing, ubiquitous webcam hardware present in modern faculty devices, the institution bypasses the exorbitant capital expenditure associated with proprietary fingerprint or RFID scanning hardware, instantly realizing a return on investment.

1.3 Scope Definition

Component In Scope Out of Scope
Student Portal Biometric self-enrollment, Analytics dashboard, Personal report downloading (CSV/PDF). Native mobile application distribution (iOS/Android App Stores).
Teacher Portal Live WebRTC video scanning, Subject management, Manual database editing, Aggregate report generation. Automated grading integration with third-party LMS platforms (Canvas, Blackboard).
Administration Immutable Audit Logging of all database changes, Defaulter (<75%) calculations. Physical campus security gate hardware integration.

1.4 Stakeholder Identification

The system impacts three primary stakeholder tiers. Students (Primary Targets) interact with the system passively during roll call and actively during enrollment. Educators (Primary Operators) rely on the UI dashboard to execute complex facial inferences without needing technical knowledge. System Administrators (Regulatory Monitors) utilize the generated Audit Logs to enforce database governance and investigate malicious manual edits.

2.2 Non-Functional Requirements

NFR-1 (Performance): Client-side tensor operations must process video frames at ≥ 15 FPS. NFR-2 (Security): Facial data must be strictly serialized as float arrays; raw images must never touch the database. NFR-3 (Availability): Backend must seamlessly execute bulk inserts of 100+ attendance records in < 2 seconds.

2.3 Use-Case Analysis & Requirement Prioritization

The system utilizes the MoSCoW methodology. Must-Have features include facial recognition, relational database integrity, and manual overrides. Should-Have features include PDF exports and Audit Logs. Could-Have features (future scope) include automated Email alerts for defaulters.

5. System Architecture Design

5.1 Frontend & Backend Architecture

The platform utilizes a Monolithic ASGI architecture. The Backend is powered by FastAPI and Uvicorn, achieving ultra-low latency through Python's asyncio core. The Frontend eschews heavy frameworks (like React) in favor of Jinja2 Server-Side Rendering infused with TailwindCSS. This ensures instantaneous Time-to-Interactive (TTI).

5.3 Database Schema Design (Entity Relationship)

The backend normalizes data across distinct relational tables to prevent orphaned records while utilizing Foreign Keys efficiently.

Module 2: Implementation, Testing, Deployment & Evaluation Phase

6. Application Development

6.1 Frontend & UX Implementation

The User Interface, codenamed "Synapse Sentinel," was constructed using custom Tailwind theme configurations (tailwind.config.js inside script tags). Extensive DOM manipulation was required for the video streaming interface. A critical CSS bug caused the <canvas> element to inherit the video's transform: scaleX(-1) mirroring effect, leading to backward text rendering. This was algorithmically corrected using JavaScript to invert Cartesian X-coordinates in real-time.

6.2 Backend & Data Processing Implementation

Over 15 distinct RESTful API routes were engineered. The most sophisticated implementation involved the fpdf2 library. To prevent server disk bloating on cloud platforms, the backend dynamically calculates column widths, iterates over SQLAlchemy relational objects, and generates raw PDF byte-arrays directly within RAM, streaming them to the client via a custom Response class.

7. Integration & System Testing

7.1 Testing Methodologies

8. Application Deployment

8.1 Cloud Deployment Architecture

The application was deployed to the Render Cloud Platform. The deployment architecture utilized a direct GitHub repository hook. Upon commits to the `main` branch, Render automatically spins up a Linux container, executes `pip install -r requirements.txt`, and launches the ASGI server via `python -m uvicorn main:app --host 0.0.0.0 --port $PORT`. The platform automatically provisions SSL/TLS certificates, ensuring all WebRTC camera traffic operates over a secure HTTPS protocol.

8.4 Server Constraints

A significant constraint of modern PaaS deployments (Render, Heroku) is the Ephemeral Filesystem. Because the SQLite database (`attendance_v5.db`) resides on the local disk, it is entirely wiped upon server sleep cycles. While acceptable for the development and academic evaluation phases, a true production rollout mandates migrating the SQLAlchemy URI to a managed PostgreSQL cluster (e.g., Supabase, Neon).

9. Performance & Security Testing

9.1 Edge Computing Load Management

Load testing demonstrated that centralizing computational logic would be catastrophic. By utilizing `face-api.js`, the massive 10+ megabyte neural network weights (SSD Mobilenet v1, Face Landmark 68Net) are cached natively in the user's browser, and the tensor calculations are executed by the user's localized GPU. This edge-computing paradigm ensures the central FastAPI server is entirely unburdened, tasked only with lightweight JSON packet routing.

9.3 Security Validation

Security validation confirmed the integrity of the Immutable Audit Ledger. Every database mutation explicitly triggers an un-blockable write to the `AuditLog` table. Furthermore, biometric security protocols dictate that raw JPEG/PNG image data is never transmitted. Only irreversible mathematical float arrays (128 Dimensions) are stored in the database, rendering biometric theft impossible even if the SQLite database is compromised.

10. Final Documentation

10.1 Report Generation Capabilities

The finalized software dynamically produces three critical data structures natively: 1) Aggregate Class Percentages, 2) Exhaustive Micro-Histories for individual students, and 3) The Defaulter Blacklist, which algorithmically isolates users who fall below a strictly coded 75% attendance threshold.
